# 批量执行的 EventKit 生命周期与自然语言答复

## 本次真机记录

2026-09-30 的八事项长测试，模型清点、生成、复核均一次完成，共35.854秒，路由为新建，完整保留8项。手机在前台执行，执行位置为 `iphone_native_app`，并未发生模型中断或后台窗口到期。

实际结果为4项保存并验证、1项保存但读回缺失、3项未尝试保存。第5项报 `readback_missing`；其后冲突查询均报“没有可读取日历”。不能把这个结果写成全部成功，也不能把第5项当作未保存后自动重建。原始任务与日历标识只保留在忽略的本机目录。

代码审计发现每项冲突查询、每项独立读回都创建新的 `EKEventStore`，查询来源、修改候选读取也反复创建。八项会产生十多个短生命周期连接；旧测试替身没有模拟实例开销或缓存，未覆盖这一风险。Apple 当前 SDK 的 `EKEventStore.h` 与[官方文档](https://developer.apple.com/documentation/eventkit/ekeventstore)建议保留长期实例；`reset()` 会使该实例先前获取的对象失效。

这证明了实现存在生命周期问题，但没有采集设备 EventKit 守护进程日志，不能断言命中了某个特定连接上限，也不能保证它是本次读取故障的唯一原因。修复是否解决真机连续写入，仍须新版验收。

## 修复

- 原生宿主共用固定两个 EventKit 实例：写入连接与独立查询/验证连接。不随事项数量增加实例。
- 在主线程同步操作边界调用 `reset()` 再重新取对象，以便看到手动修改/删除；不跨 reset 或 await 保留 EventKit 对象，不把不同 store 的对象混用。独立读回仍按真实标识或发生区间重新查询，不使用刚保存的内存对象充当验证。
- 日历列表为空时明确返回接口不可读，不推断用户没有安排；删除后验证也先确认日历可读，不能把读取故障当作删除成功。
- 原有写入前预约记录、幂等账本、冲突检查和不明结果不重写策略保持不变。没有自动重跑或修改本轮已保存事项。

## 自然语言答复

原来只有查询任务调用 `tool_answer.py`，新建、排程和改删结果仍直接显示状态卡。这是用户看到结构化回答的原因。

新增任务版本8：手机完成真实执行并持久化后，生成独立 `completion_source_id`；Mac 取得本轮有限执行记录，复用 `tool_answer.py` 生成并复核自然语言回复。主对话显示回复，字段、数量和实际读回保留在“查看执行依据与详情”内。

发送给模型的数据包括原需求、本轮计划/修改决定、逐项保存和验证状态、读回字段及失败原因。导出过滤持久事件标识、设备状态、任务附加标记、无关日历占用明细及聊天历史。v7及以前旧记录不会因升级自动上传生成回复。手机设置中已说明这条数据路径。

回答和日历执行分开持久化：回答延迟、失败或断连重送，不会重做已完成写入。回答的 source 必须对应本轮实际结果，已保存回答不可覆盖；模型说“全完成”也不能把 `partial` 或 `unknown` 升级为 `verified`。不以代码模板代替失败的模型回答。

## 验证与限制

- `scripts/test.sh`：Python回归、Foundation协议验证，以及EventKit替身回归。
- `eventstore_lifetime_validation.swift`：注入最多两个实例、读缓存不自动刷新；8项混合事件仍全部保存并独立验证，重复请求不增加保存次数，手动修改/删除可被新查询看到。该上限是测试注入，**不是对真实 iOS 连接上限的声称**。
- `completion_answer_validation.swift` 与 `test_completion_answer.py`：旧任务拒绝导出、来源对应、真实状态不被改变、部分结果/空值保留、持久化、回答重送不重复操作、回答失败不触发写入。
- `python3 scripts/check_completion_answers.py --live`：两份合成执行记录调用真实模型，分别为全部验证与4成功/1已保存未验证/3未保存；没有访问手机或上传私人记录。回复样本见 `evidence/completion-answer-model-probes.json`。

执行仍依赖 Mac 和 iOS 有限后台窗口；若执行已完成而回复尚未送达，回来后同步回复即可，无需重新执行。模型语义与设备保存仍须分别验收。
