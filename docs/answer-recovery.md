# 自然语言答复恢复与事项清点纠错

## 解决的问题

原先清点模型可能把活动的备注或链接拆成新事项、漏掉时间未知的预约。固定首次清点数量的 schema 会保留这个错误。答复模型还可能把计划当作实际执行结果；复核返回 `correct` 却没有修正正文时，任务卡片只留下失败提示。

## 当前流程

1. **清点 → 活动边界审查 → 计划 → 计划复核**：短小的模型审查先区分活动与附属信息，未知时间的活动仍保留；代码仅在计划生成前分配顺序 ID。初稿数量不再锁进 schema。计划复核仍可同时修订完整清单与计划，必须有原文依据，最终覆盖一致才可执行。执行过的 ID 不会重排。
2. **真实接口结果 → 模型答复 → 逐项事实复核**：按事项 ID 对齐原计划与实际结果，保留原始接口记录。计划里的备注、链接或时间不能证明保存成功。复核提取最终正文对每项状态的断言；代码检查 ID 覆盖、重复和保存/核验状态一致性，文字含义由模型判断。
3. **有界修复**：结构化复核使用嵌套 `anyOf`，`correct` 必须带完整正文。格式矛盾、事实状态不一致、漏项或阻断会将具体错误反馈给模型，再修复一次。答复生成和两轮复核共用 120 秒，沿用现有传输重试与持久化检查点。失败仍明确显示，不使用代码模板冒充模型回答。
4. **用户主动重新生成答复**：执行卡片或查询卡片失败后有此按钮。手机持久化独立 `answer_retry_id`；Mac 归档上次答复错误、模型结果和检查点，为这次答复开启新的有界预算。复用原接口快照，不查询当前日历、不重新理解计划、不调用创建/修改/删除。执行结果、事项 ID、source_id 和写入 lease 保持不变。旧重试编号的答复与失败回包会被拒绝。
5. **分别呈现执行与答复状态**：等待或答复失败时仍显示原日历执行摘要。已完成的模型答复先落盘再送到手机；断线只重送答复。重新生成时模型会说明依据的是当时记录，不保证手动更改后的当前日历仍相同。

不会自动补答旧协议任务。只有已有查询快照且版本 >=5，或已有执行答复快照且版本 >=8 的失败任务可主动重试。不会为未导出过的旧报告创建新的数据共享路径。

## 验证

- `bash scripts/test.sh`：Python、Foundation 和 EventKit 测试替身；含漏项/多算纠正、矛盾复核恢复、假成功状态拒绝、答复投递丢失、手动重试与过期回包拒绝。
- `python3 scripts/check_completion_answers.py --live`：完全合成的八事项完整成功、部分成功记录，仅调用模型。
- `python3 scripts/check_answer_recovery.py --live`：完全合成的六项误清点纠正为五项、1 项成功 + 3 项冲突 + 1 项缺时间，以及故意注入错误答复与 `correct + null` 后恢复。
- 最初仅用合成记录验证。修复版安装后，用户明确授权仅将最近失败任务的原文及当次执行记录重新交给已配置模型，并在手机点击“重新生成答复”；未携带历史对话，未重跑日历。

原始失败示例仅留在本机；仓库 evidence 只保存合成验证。结构化输出确保格式，不保证语义完全正确；逐项模型复核也可能误判。依据：[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)。

本轮结果：107 项 Python 测试、9 个 Foundation 程序、5 个 EventKit 测试替身程序及签名 iOS 构建通过。五种模型验证（完整成功、部分成功、混合结果、矛盾复核恢复、错误清单纠正）通过。早期清单失败记录保留，最终清单通过结果见 `evidence/answer-recovery-inventory-probe.json`；汇总见 `evidence/answer-recovery-validation.json`。修复版已安装并启动，Mac 服务与手机 RPC 已连接，日历为完全访问，未开启写入窗口；用户随后主动点击补答，手机持久化回答状态 complete，Mac 收到 acknowledged，耗时 11.973 秒。原任务保持 partial，原写入发送记录仍只有一次且执行时间未变化。本次未独立观察屏幕渲染；旧任务误拆的备注条目保留在历史计划，重生成答复不重写历史清单。
