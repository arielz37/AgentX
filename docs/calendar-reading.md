# 查询已有日程、空闲与冲突

## 使用

更新 AgentX App 后重启 `启动 AgentX.command`，保持手机连接 Mac。当前 RPC 协议为 5，不兼容仍运行的旧 worker；历史任务保留，新提交使用 v7。打开 **AgentX → 设置 → 准备连接和日历权限**，允许完全访问。执行任务时不会临时弹出权限请求。写入权限不足以读取日历。

在全能助手或日程助手输入：

- “明天有哪些安排？”——手机展示日期范围内的已有事件。
- “2026年10月2日下午三点到四点有冲突吗？”——检查这个时段是否已有日历占用。
- “下周一到周五，每天14点到18点，找至少90分钟的空档。”——返回足够长的连续可用区间。

点发送后可留前台，也可切回游戏；回来先看到自然语言回答，例如“14:00–15:00、16:00–18:00都可以安排事情”。点击“查看依据与完整结果”才展示查询参数、占用来源和完整列表。回答由大模型根据原始问题和实际接口数据生成，另做一次事实复核，不使用代码拼接正文或模板兜底。用户另行提交具体时间创建时，会先检查占用，冲突则本项不创建；报告显示实际冲突区间及检查覆盖范围，不自动改期。查询不会写入事件，测试模式也不会缩小查询到测试事件。

## 实现与隐私

Mac 两次模型请求负责理解及独立复核，生成不可变 `CalendarQuery`。参数校验和范围白名单通过后，手机 `CalendarReader` 调用 [EventKit 日期范围谓词](https://developer.apple.com/documentation/eventkit/ekeventstore/predicateforevents(withstart:end:calendars:))，按发生项读取重复日程，不按系列 ID 合并。同一 iPhone 上执行，不使用 Mac EventKit 或云日历。

v5 及以后提交的查询成功后，会将本次范围内的标题、开始/结束、全天标记、所属日历、占用依据及候选空档，经 Mac 发送给已配置的 OpenAI 模型。v7 最多2000条事件明细和2000个候选区间，携带总数和截断标志（旧版100/20）；普通查询不发送备注或联系人。新提交可携带同助手最近六轮对话及事件摘要，修改候选另包含地点、备注、链接，详见 calendar-editing.md。模型时间表示统一为查询时区，原始接口快照仍单独保留。这里的“直接使用接口数据”允许必要的无损时区转换与参数校验，不允许代码生成回答正文。

常规轮询仍不携带全部事件数组。新任务通过特定任务的 `plan_answer_context` 或首次查询响应取得同一份持久快照，绑定 `query_result_id`。读取完成为 `answer_pending`，模型回答完成才是 `query_complete`；失败为 `answer_failed`，不会否认已完成的读取。Mac 将模型正文持久化后才交给手机；断连恢复只补送相同正文，不重复模型调用或日历操作。手机后台窗口结束后，Mac 可以完成模型步骤，但手机显示可能需等恢复连接。

旧 v3/v4 记录不会自动走这条数据上传路径。新回答及其依据会存在手机和被Git忽略的 Mac `data/`；API 请求沿用 `store:false`，不将其解释为第三方零保留承诺。详情见 [模型回答流程](model-answers.md)。

## 明确边界

- 一次查询最多一个当地日历年（包含闰年）。未指定日期默认今天；“最近”可默认未来7天。空档默认至少60分钟，每日09:00–21:00，报告列出默认条件。
- 展示全部可访问日历，包括测试事件，但“展示”和“占时”分开。取消事件忽略；标记“空闲”的事件不占时；识别到的只读节假日订阅默认仅展示。其他日历的个人全天活动、工作订阅等仍参与忙闲计算，未知忙闲状态保守占时。没有日历或权限不足明确失败，不解释为“空闲”。
- **设置 → 参与忙闲计算的日历**可逐个覆盖默认规则，选择仅展示的日历。偏好只存在手机，不修改系统日历；影响后续查询和写入前检查，旧报告不会自动重算。默认节假日识别要求同时满足只读、订阅及日历名称为节假日类（中文后缀“节假日/节日”及繁体，英文“holidays”等）；不是按事件标题、10月2日或“全天”直接排除。它是有限命名启发式，不是系统提供的可靠节假日类型。陌生日历默认参与，漏识别/误识别可手动切换。日历完全重新同步造成标识变化时应重新检查设置。
- 半开区间：一件事10:00结束，下一件10:00开始不冲突。跨天、全天占用按 EventKit 实际返回边界计算；没有重新引入旧的全天写入修正。过去的时间不作为空档。
- v7 接口列表最多2000条，空档最多2000段；占用计算使用整个范围，超过2000个发生项则拒绝查询、要求缩小范围，不能用截断数据宣称空闲。
- v7 新建前检查单次完整区间；重复系列展开首次起一年内各次发生，有限系列若全部覆盖则标 full_series，否则标 one_year_horizon。未知夏令时边界和超量数据拒绝放行。历史任务保留原版本行为。
- 空档是查询时快照，未预留；未同步到手机的安排不在结果中。检查和保存之间不是数据库事务，外部同时新增仍可能冲突。
- v7 支持读取后自动排程、修改/删除，以及同助手最近六轮跨消息指代；重复自动排程、改动重复规则、带邀请人事件的修改仍未实现。
- 仍需 Mac 和有限后台窗口，查询也使用同一45秒租约；超时不会自动重新执行。只读任务恢复前台后也不会偷偷重查，结果时间在报告中。
- 自然语言日期和最终正文仍由模型决定，复核不能保证永远正确。报告保留实际接口范围、数据与模型正文，不能用模型叙述替代执行证据。

- 真机前台：用户提交的“查询明确日期日程”和“指定下午窗口找一小时空档”均由手机返回 `query_complete`；原始查询结果没有进入 Mac RPC，返回的是摘要。用户随后指出空档错误（节假日误算占用，见下文）。**真机冲突阻止写入和新版后台查询仍待完成**，不得沿用旧创建功能的验收结论。原始执行记录仅在本机 `data/`，不提交设备日志。
- 真实模型采用合成输入，不访问手机。开发中发现每日小时被误填为分钟、范围扩大到周末，以及超限/自动安排请求错误放行。增加字段单位、显式边界说明和复核可见的实际钟点/日期列表；最终6例全部通过，见 `evidence/calendar-query-model-probes.json`。保留这些局限，不能据少量测试声称模型零错误。

真机验收顺序：先只查一个已有测试事件的明确日期，人工核对列表；再查相同占用区间和可用空档；最后仅在用户允许后提交一条与既有测试事件冲突的新建请求，确认未新增。另在游戏期间执行只读查询并核对报告中的后台状态。不要以截图或 UI 自动化读取用户其他 App。

## 2026-09-30 忙闲误判修复

用户确认 10月2日只有15–16点个人安排，另一条为国庆假期。旧版读取6个日历的两条事件，把两条都算占时，导致14–18点没有空档。查询日期、时长和单位正确；以单条15–16点重放算法会正确得到14–15、16–18，加上全天占用则归零。因此根因是来源/占用策略：`availability != .free` 将节假日信息也当作个人忙碌，且空档报告隐藏了占用依据。

修复分为：可展示但不占时的节假日来源策略、逐日历用户覆盖、手机占用依据，以及自然语言优先的回答。没有跳过所有全天事件，没有用 LLM 重新猜用户是否忙碌，没有修改日历里的国庆假期。真实订阅类型和默认识别在更新后仍需手机验收。

新增回归覆盖：14–18点仅15–16点占用；只读节假日加个人安排；个人全天活动和工作订阅继续占时；用户强制计入/排除；空档与新建冲突采用同一策略；查询结果对应实际区间。自 v5 起正文改由模型回答，回归另覆盖单任务数据导出、旧任务不上传、绑定快照及断连只补送回答。
