# 两条口语短测试的真机问题与修复

本轮原话为“下周帮我找一天整理下家里的东西……挑个没安排的日子”，随后“刚才那个改叫整理书房吧……其他都不变”。用户也会在系统日历手动修改或删除，属于正常使用场景。

## 已观察到的问题

1. 全天查询被复用了定时自动排程的180分钟限制。模型填写了480分钟，即使 slot_kind=all_day、实际使用 duration_days，也被拒绝。
2. 两个不同任务 ID 都记录了保存，但全天读回是空时区、当地最后一天23:59:59。原验证按定时事件要求时区字符串相同、结束时间差小于1秒，误报未验证。原始读回保留，不代表用户目前日历仍有两条；用户确认已手动删除部分测试事项。
3. 一次再次提交被模型路由为直接新建，绕过本轮空档查询；保存前冲突检查不等同于先读取空档再择时。
4. 上下文仅选 status=verified，遗漏已保存未验证事项；自动排程失败后又将查询到的旧日历事项作为任务的 events，污染“刚才那个”的含义。
5. 回放发现仅靠文字提醒，模型仍可能在最近事项被删除后选择更早的相似事项；测试标题前缀及完全相同候选也暴露出执行契约问题。

## 修复

- 定时事项才执行180分钟上限；全天按当地日期数验证，不再把分钟占位误当执行时长。首轮复核拿到实际契约错误，并先核对是否必须查询空档，不能凭旧对话里的建议日期直接新建。
- 全天日期验证接受两个明确的读回边界：排他次日零点，或该零点前恰好1秒；允许浮动事件空时区。仍要求同样的起始日期、同样的覆盖天数与全天标记。多出一天、任意非边界时间及定时事项偏差不会因此放行。保留原始值与验证依据；标题、备注等修改不重写未要求改动的全天日期。
- 上下文记录保存状态、验证状态和来源，不把未验证等同于没创建；写入结果与查询到的旧事项分开。最近相关事项即便未验证，也可以作为本轮重新定位的线索。
- 模型在首轮通过 `query.target_history_refs` 选择所指历史事项；随后读取真实候选并形成修改决策，手机与 Mac 校验候选必须属于同一个已绑定目标。模型负责理解指代，代码不按“刚才”等关键词替它选择。
- 单次非重复事项的设备 EventKit 标识仅留手机；对已绑定历史目标定向查当前事件，允许它被用户手动改名/改期后移出原日期范围。候选通过临时引用和 `related_history_refs` 关联，不把设备标识交给模型。标识因同步等原因失效则不能凭相似标题替换。重复系列仍用发生项范围查询，不通过标识误取首个发生项。
- 删除是正常 not_found 结果，不重建、不改更早的事件。手动改动后以当前候选为准应用最小补丁；若在模型决策和写入之间再次变化，指纹检查停止写入，避免覆盖。没有跨应用事务锁，不能承诺所有竞态都自动恢复。
- 测试前缀由执行层保留；无法区分、没有唯一历史关联的相同候选不能凭列表顺序挑选。复核失败的原始模型决策和原因保存在本机忽略目录，便于排查。

## 验证及数据边界

新增回归覆盖真实全天读回形状、不可接受的额外一天/非边界结束、已保存未验证的上下文、查询占用不冒充创建结果、分钟与全天分离、历史目标绑定、手动改期移出范围后的定向定位、手动删除后不误改旧事项，以及测试前缀。

`python3 scripts/check_short_test_regressions.py --live` 使用原口语请求和合成日历，只调用模型，不访问手机或写日历。结果在 `evidence/short-test-model-regressions.json`，修复前失败样本另存。真实用户/设备记录仍仅存 `data/`、`artifacts/`。新提交会使用同助手最近六轮摘要；只有模型已绑定的近期单次事项进行定向读回，其当前日期可能在历史查询范围之外，这属于当前请求所指的同一事项。

不自动重放失败任务，不自动删除、合并或修改本轮旧测试事件。构建和合成验证不代替安装后的真机重测。

本轮66项 Python 测试、8组 Swift 校验、4组 EventKit 替身程序通过，签名构建通过；最终7个真实模型合成回放样例全部通过。汇总见 `evidence/short-test-repair-validation.json`。用户确认方便更新后，修复版已安装且 devicectl 启动成功，Mac 独立服务已重启。安装后初次只读 RPC 超时；用户手动准备连接后复查通过：AgentX 原生宿主在前台、协议版本5、日历完全访问。尚未完成安装后的真实业务重测，不将连接检查、构建或合成回放计为业务真机通过。
